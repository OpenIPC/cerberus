# cerberus

[English version](README.md)

Облачный агент для камер OpenIPC: маленький демон на C, который живёт **внутри прошивки камеры** и
включает камеру в приватную WireGuard-сеть — так, что видео, ONVIF, настройки и SSH доступны откуда
угодно, а между камерой и облаком нет ничего, кроме туннеля.

Делает ровно пять вещей:

1. заводит ключевую пару X25519 и claim-код — один раз, на первом старте;
2. энроллится в координатор по TLS (`POST /enroll`) и забирает join-материал;
3. кладёт ключ, claim-код и join-материал в **U-Boot environment** через `fw_setenv` (файл —
   фолбэк) — единственное место на камере, которое переживает перепрошивку;
4. поднимает из него `wg0` и следит за туннелем с двух сторон: возраст хендшейка из `wg` **и**
   ICMP-проба хаба *внутри* туннеля — свежий хендшейк на мёртвом пути выглядит как живой;
5. шлёт живость через `POST /nodes/{id}/heartbeat` и применяет то, что приезжает в ответе:
   сменившийся join-материал и одноразовые команды.

Единственная зависимость — **mbedTLS** (TLS, X25519, SHA-256, base64, CTR-DRBG), всё остальное — libc.
Агент рулит kernel WireGuard, который в прошивке уже есть, поэтому весит десятки килобайт, а не
целую userspace-реализацию WireGuard.

## Установка на камеру

Обычный путь — одна строка по SSH с токеном энролла из панели облака:

```sh
curl -fsSL https://cloud.openipc.ru/install.sh | sh -s -- tok_...
```

Установщик (здесь это `bootstrap.sh`) спрашивает у камеры её процессор (`fw_printenv -n soc`),
скачивает сборку под него, ставит `/usr/sbin/cerberus` и `/etc/init.d/S99cerberus`, пишет адрес и
токен в U-Boot env и запускает агента. Если что-то не так, он печатает короткий код —
`cerberus: E13` — и страницу, где код расшифрован:
<https://cloud.openipc.ru/docs/openipc-camera/#codes>. `uninstall.sh` снимает всё обратно.

Руками, из тарболла релиза:

```sh
tar xzf cerberus-<version>-linux-musl-armv7.tar.gz && cd cerberus-<version>-linux-musl-armv7
./install.sh                 # /usr/sbin/cerberus + /etc/init.d/S99cerberus
fw_setenv streq_api https://cloud-api.openipc.ru/v1
fw_setenv streq_enrollment_token tok_...
reboot                       # или: /etc/init.d/S99cerberus restart
```

Init — BusyBox, не systemd: `S99cerberus` читает конфиг из U-Boot env и запускает `cerberus run`
через `start-stop-daemon`. Обновление — заменить бинарь и перезапустить службу; ключ, node id и
claim-код лежат в U-Boot env и обновление переживают.

Токен, выписанный в панели на одну камеру, привязывает камеру к тому, кто его выписал. С токеном
партии агент печатает claim-код (его же показывает `cerberus status`), который вводят в панели,
чтобы забрать камеру себе. До этого камера в сети, но смотреть её и командовать ей некому.

### Что должно быть на камере

| нужно | зачем | если нет |
|---|---|---|
| kernel WireGuard + `wg` | весь data plane | агент бесполезен |
| `ip` | адрес и линк на `wg0` | то же |
| `fw_setenv` / `fw_printenv` | хранилище, переживающее перепрошивку | фолбэк в файл (и он не переживёт) |
| разделяемый mbedTLS | TLS, X25519, SHA-256 | статическая сборка |
| `ping` | проба внутри туннеля | проба выключается с предупреждением, присмотр за хендшейком остаётся |
| `reboot` | команда `Reboot` | команда логируется как невыполнимая |

## Сборка

```sh
make                                   # нативно, против системного mbedTLS
make STATIC=1                          # статически
make VERSION=1.2.0                     # версия, которую агент сообщает (по умолчанию — из main.c)
make install DESTDIR=/tmp/rootfs       # /usr/sbin/cerberus + /etc/init.d/S99cerberus
```

Собирается против обоих поколений mbedTLS, что встречаются в поле: 3.x и 2.28 LTS — последний лежит
в Buildroot и, значит, в большинстве прошивок эпохи OpenIPC.

Тарболлы релиза собираются в контейнерах, хосту нужен только Docker:

```sh
ci/build.sh musl-armv7                 # OpenIPC на ARMv7: статический musl, без зависимостей
ci/build.sh armhf arm64 amd64          # обычные SBC (glibc, динамически)
                                       # → dist/cerberus-<version>-linux-<arch>.tar.gz (+ .sha256)
```

**glibc-сборка на OpenIPC не запускается вообще.** Прошивка на musl: glibc-бинарь просит загрузчик
`/lib/ld-linux-armhf.so.3`, которого нет, и `sh` отвечает `not found` про файл, лежащий перед
глазами. Отсюда отдельная сборка `musl-armv7`. Она идёт внутри эмулированного armv7 Alpine
(binfmt/QEMU — в Docker Desktop есть; на голом Linux один раз
`docker run --privileged --rm tonistiigi/binfmt --install arm`), поэтому кросс-тулчейн не нужен:
libc ровно та, что в прошивке. Сборка статическая, mbedTLS внутри — неважно, какой mbedTLS несёт
прошивка и несёт ли вообще.

Посмотрите на камеру, прежде чем выбирать сборку:

```sh
uname -m                                    # armv7l → musl-armv7 годится; mips/mipsel → нет
grep -i features /proc/cpuinfo | head -1    # нужен vfp: ARMv5 без него armv7-код не запустит
ls /lib/ld-musl-* 2>/dev/null               # подтверждает, что прошивка на musl
ls /usr/lib/libmbedtls* 2>/dev/null         # есть свой mbedTLS → можно линковать динамически
```

Ingenic T20/T31 — это MIPS, а у ARMv5 нет VFP; обоим нужен тулчейн самой прошивки (Buildroot):

```sh
make CC=mipsel-openipc-linux-musl-gcc MBEDTLS=<buildroot-staging> STATIC=1
# или, если mbedTLS в прошивке есть и версия совпадает, без STATIC=1 — десятки КБ вместо сотен
```

`STATIC=1` разумен только с musl: статический glibc всё равно тянет в рантайме разделяемые
NSS-библиотеки для `getaddrinfo` — ровно того вызова, которым резолвится хаб.

### Сколько весит

`-Os`, `--gc-sections`, strip; мерено по тарболлам из `ci/build.sh`:

| цель | байт |
|---|---|
| armv7, musl, статически — OpenIPC | 538 080 |
| armv7, glibc, динамически (armhf) | 26 568 |
| arm64, glibc, динамически | 68 568 |
| x86-64, glibc, динамически | 44 120 |

Сам агент — это динамическая armv7-цифра. Почти всё в статической сборке — mbedTLS в том виде, в
каком его собирает Alpine: сервер, DTLS, RSA, все наборы шифров. Прошивка собирает mbedTLS со своим
конфигом (TLS-клиент, ECDHE + AEAD, X.509), и статический агент против него в разы меньше.

В работе это один процесс, один поток, около 1,4 МБ RSS — в основном буферы mbedTLS на время
TLS-хендшейка. Каждый heartbeat — новое TLS-соединение, ~4 КБ по сети, так что при 20 секундах по
умолчанию это ~17 МБ в сутки; на мобильном тарифе `STREQ_HEARTBEAT=60` делит счёт на три — ценой того,
что команды и ротация доедут на столько же позже.

## Тесты

```sh
make test                                                  # Alpine: musl + mbedTLS 3.x
CERBERUS_TEST_IMAGE=debian:bookworm-slim tests/run.sh      # glibc + mbedTLS 2.28
```

Нужен только Docker. Набор собирает агента с `-Werror` и гоняет его против поддельного координатора
(`tests/fake_coordinator.py`) по настоящему TLS со своим CA:

- **личность** — ключ X25519 тот же, что выводит `wg pubkey`, лежит в сторе и больше нигде, стор
  0600, ключ из старого файла переносится без изменений;
- **TLS** — чужой CA и сертификат на другое имя отвергаются раньше, чем уйдёт хоть байт запроса;
- **энролл** — в запросе публичный ключ и `sha256(claim-код)`, но никогда не сам код; join-материал
  сохраняется; повторный энролл ничего не тратит;
- **обратный канал** — `Restart` перезапускает агента, `Reboot` перезагружает, неизвестные команды
  игнорируются, переехавший или сменивший ключ хаб подхватывается с перепрограммированием
  интерфейса, недоступность координатора — одно предупреждение и пережита, отозванный узел
  выбрасывает энролл и останавливается;
- **старт** — недоступный координатор пережидается с отступом, SIGTERM в паузе выполняется сразу;
- **data plane** — настоящий kernel-WireGuard туннель до хаба в отдельном network namespace:
  хендшейк, ping по туннелю, и украденный маршрут, который видит проба внутри туннеля и чинит
  пересборка интерфейса;
- **поставляемые скрипты** разбираются шеллом, а в установщиках нет комментариев.

Для data plane на хосте нужен kernel WireGuard (любой свежий Linux, VM Docker Desktop); без него
секция пропускается, а `REQUIRE_WG=1` превращает пропуск в провал — так запускает CI.

## CI и релизы

`.github/workflows/ci.yml` на каждый push и pull request гоняет shellcheck, тесты на обоих поколениях
mbedTLS и собирает четыре тарболла. Тег `v*` публикует эти же тарболлы с `.sha256` как GitHub
release; версия, вкомпилированная в бинарь, берётся из тега.

```sh
git tag v0.2.0 && git push origin v0.2.0
```

## Запуск

Конфиг — переменные окружения `STREQ_*`; `S99cerberus` заполняет их из U-Boot env.

| переменная | по умолчанию | смысл |
|---|---|---|
| `STREQ_API` | `https://api.localhost/v1` | база координатора, включая `/v1` |
| `STREQ_ENROLLMENT_TOKEN` | — | одноразовый токен от владельца |
| `STREQ_KIND` | `Camera` | тип узла |
| `STREQ_HOSTNAME` | — | имя, под которым камера появится в панели |
| `STREQ_IFACE` | `wg0` | интерфейс WireGuard |
| `STREQ_SUBNET` | `10.80.0.0/16` | фолбэк: подсеть сети и адрес хаба приезжают в join-материале |
| `STREQ_CA` | `/etc/ssl/certs/ca-certificates.crt` | файл или каталог доверенных CA |
| `STREQ_INSECURE` | `0` | отключить проверку TLS (только для отладки) |
| `STREQ_STORE` | `auto` | `auto` \| `uboot` \| `file:/path` — здесь же лежит и ключ |
| `STREQ_KEYFILE` | `/etc/streq/wg.key` | старое место ключа; при первом же виде переносится в стор |
| `STREQ_KEY_TMP` | `/tmp/.streq-wg.key` | куда ключ кладётся на время одного `wg set` |
| `STREQ_HEARTBEAT` | `20` | секунд между heartbeat; `0` — выключить |
| `STREQ_PING_TARGET` | хаб | кого пинговать внутри туннеля |
| `STREQ_PING_INTERVAL` | `60` | секунд между пробами; `0` — выключить |
| `STREQ_PING_TIMEOUT` | `3` | сколько секунд ждать ответа на одну пробу |
| `STREQ_PING_FAILS` | `3` | неотвеченных проб подряд до пересборки интерфейса |
| `STREQ_STALE_AFTER` | `180` | секунд без хендшейка до перетыкания пира |
| `STREQ_RETRY_MIN` / `STREQ_RETRY_MAX` | `5` / `300` | отступ повторов энролла, секунды |
| `STREQ_DRY_RUN` | `0` | печатать команды `ip`/`wg`, а не выполнять их |

Ключи U-Boot env, которые читает `S99cerberus`: `streq_api`, `streq_enrollment_token`,
`streq_hostname`, `streq_ca`, `streq_subnet`, `streq_ping_target`, `streq_ping_interval`,
`streq_iface` (все, кроме первых двух, необязательные; пусто — по умолчанию). `streq_ca` важнее, чем
кажется: в прошивке может не быть бандла CA вовсе, и тогда энролл падает на сертификате координатора,
а поправить это без перепрошивки нечем — укажите путь к корневому сертификату (ISRG Root X1 для
Let's Encrypt).

```
cerberus run       # enroll + up + watch (по умолчанию; это запускает S99cerberus)
cerberus enroll    # только энролл, идемпотентно
cerberus up        # поднять интерфейс из сохранённого
cerberus status    # что сохранено, возраст хендшейка, отвечает ли туннель
cerberus keygen    # напечатать пару ключей (stdout — данные, диагностика в stderr)
cerberus clean     # убрать агента: интерфейс, автозапуск, сохранённое и сам бинарь
```

## Что где лежит

`streq_device_key`, `streq_node_id`, `streq_overlay_ip`, `streq_hub_endpoint`, `streq_hub_pubkey`,
`streq_allowed_ips`, `streq_network_subnet`, `streq_hub_ip`, `streq_claim_code` — всё в U-Boot env.

**Ключ там же, и это осознанно.** Прямолинейнее держать его отдельным файлом 0600, но на камере
`/etc` — это squashfs или оверлей на разделе, который перепрошивка перезаписывает, а `streq_node_id`
рядом в U-Boot env её переживает. Узел вернулся бы с личностью, на которую у хаба есть пир, и без
ключа, которым её доказывают, — а энролл пропускается всегда, когда node id сохранён. Это не
«перерегистрируется», это **насмерть**. Ключ и node id обязаны жить и умирать вместе, поэтому лежат
в одном сторе. `wg set private-key` хочет путь, поэтому на время ровно одного вызова ключ
материализуется в `/tmp` (0600) и сразу удаляется; на rootfs он не пишется вообще.

`streq_network_subnet` и `streq_hub_ip` приходят с энроллом: на инстансе с арендаторами у каждой
сети свой диапазон, и узел берёт из них маску своего адреса и отдельный маршрут до хаба. Маршрут
нужен потому, что `allowed-ips` у WireGuard — это криптомаршрутизация, а не таблица ядра: без него
хендшейк проходит, а пакеты уходят мимо туннеля.

## Control plane: REST, а не хаб

Полноценные узлы держат SignalR-соединение с координатором и получают пуши карты сети. Клиент такого
на C — не тот жанр, поэтому у тонких узлов деградированный путь:

| хаб | что делает cerberus |
|---|---|
| `Heartbeat(nodeId)` | `POST /nodes/{id}/heartbeat` раз в `STREQ_HEARTBEAT` секунд |
| `DirectiveIssued` (пуш) | ответ на тот же heartbeat — та же `NodeDirective` |
| `JoinNetwork(nodeId)` → карта | `GET /nodes/{id}/map` есть, но агент его не опрашивает |
| `NetworkMapUpdated` / `PathRevoked` | пушей нет |

Карта камере не нужна: пир у неё ровно один — хаб, и он приезжает в join-материале. `404` на
heartbeat значит, что координатор узел больше не знает (отозван или пересобран): агент выбрасывает
энролл из стора и останавливается, чтобы следующий старт зашёл заново, а не долбился мёртвым node id
до конца времён.

### Обратный канал: ответ на heartbeat

```jsonc
{
  "command": "None",          // None | Restart | Reboot — одноразовая, выдаётся ровно один раз
  "join": {                   // текущий join-материал, всегда целиком, а не дельта
    "kind": "Wireguard", "overlayIp": "10.80.0.7",
    "hubEndpoint": "hub.example:51820", "hubPublicKey": "base64…", "allowedIps": "10.80.0.7/32"
  },
  "mapVersion": 42
}
```

`join` агент сверяет с сохранённым и применяет **только расхождение**: хаб переехал (новый VPS,
новый DNS) или сменил ключ — камера перезаписывает стор и перепрограммирует интерфейс сама.
`Restart` — это re-exec самого агента (супервизора на камере может и не быть), `Reboot` — `sync` и
`reboot`.

### Присмотр за туннелем

Хендшейк и проба отвечают на разные вопросы, и ни один не следует из другого: WireGuard
переустанавливает хендшейк примерно раз в две минуты и покажет совершенно свежий, пока по туннелю не
ходит ничего — забранный маршрут, интерфейс, который занял кто-то другой, хаб, который отвечает на
хендшейк и не форвардит. Хендшейк говорит «пир на месте», и только вернувшийся пакет говорит
«туннель работает».

Лестница восстановления — по возрастанию цены, и камера обязана пройти её сама:

| что видно | что делается |
|---|---|
| хендшейку больше `STREQ_STALE_AFTER` | перетыкается пир (это же и перерезолвит имя хаба) |
| `STREQ_PING_FAILS` проб подряд без ответа | интерфейс сносится и собирается заново |
| вдвое больше — пересборка не помогла | агент перезапускает сам себя |

Камера, которая перезагружается от одного потерянного пакета, хуже камеры, которая просто лежит, —
поэтому пороги считают серии, а не события.

Отдельно — старт. `cerberus run` **не умирает от недоступного координатора**: энролл повторяется с
удваивающейся паузой от `STREQ_RETRY_MIN` до `STREQ_RETRY_MAX`, сколько понадобится. Init на камере
запускает агента ровно один раз и больше на него не смотрит, так что выход здесь означал бы камеру,
потерянную до следующего выключения питания — из-за сети, DNS или NTP, опоздавших на несколько
секунд. Ошибки конфигурации по-прежнему завершают сразу: повторы не выдумают токен, которого не
прописали.

## Чего он не делает

Пушей и P2P. `PathRevoked` ходит только через хаб — тонкий узел узнает об отзыве со следующим
heartbeat. Hole-punch идёт через хаб (`ReportCandidates` → `PunchNow` → `ReportPathState`) и требует
одновременности, которой опрос не даёт, поэтому этот агент остаётся на пути через хаб — ровно на том
пути, который работает всегда.

Видео через агента не идёт вовсе: релей тянет `rtsp://{overlayIp}:554/stream0` прямо с камеры по
туннелю.
